# تكامل العميل والشيف — التنفيذ والاختبار المحلي

تم التنفيذ بموافقة صاحب الطلب للتجربة المحلية والمحاكي فقط. هذه ليست موافقة
الفريق على الدمج أو الإنتاج. لا تنشر القواعد ولا تفعّل مزود مصادقة في مشروع حي.

## ما تغير

- OrderModel الحالي يحتوي customerId اختياريًا؛ المستند القديم يبقى بلا مالك.
- CustomerIdentityService يعيد استخدام هوية Auth الموجودة، أو ينشئ ضيفًا مجهولًا
  عند غيابها بعد الاستعادة. يجمع طلبات التهيئة المتزامنة ولا يستبدل جلسة موظف.
- AuthCubit يحافظ على الضيف دون مستند users، ويعيد الموظف إلى مساره المعتاد.
- CustomerOrderCubit يحفظ UID وcreated_at من الخادم، ويحتفظ بتسلسل السلة ثم
  تسجيل طريقة الدفع. يُمسح طلب الجلسة وبياناتها عند تغير الهوية، ولا تعرض نتيجة
  عملية قديمة تحت هوية جديدة. payment_data اختيار طريقة فقط وليس حالة دفع موثقة.
- /orders يستخدم استعلام الملكية اللحظي ويلغي نتائج الهوية السابقة عند تغييرها.
  IDs المحلية لا تُستخدم في المسار الجديد للتفويض أو لاستعادة الملكية.
- معاملات الشيف تظل على orders والنموذج والحالات نفسها. لا يتغير التصميم أو AR/EN.
- كل ذلك مفعّل عبر USE_FIREBASE_EMULATORS فقط. التشغيل بدون الخيار يحافظ على
  المسار السابق؛ التكامل الآمن الجديد ليس مطروحًا للإنتاج بعد.

FirebaseEnvironment يستخدم تطبيق demo مسمى منفصلًا حتى على Android، تفاديًا
للتطبيق الافتراضي الذي قد تهيئه google-services.json تلقائيًا. الخدمات ذات الصلة
تستخدم هذا التطبيق، بما فيها وصول إدارة الطهاة لتفادي اتصالها بالإنتاج في وضع
المحاكي؛ لا تتغير وظائف تلك الميزة. السلة منفصلة وكاش SQLite لا يستخدم هنا.
قواعد الإنتاج وfirebase.json وfirebase_options.dart لم تُغيّر.

## تشغيل المحاكيات وتجهيز الموظفين

من جذر المشروع، في PowerShell أولى، مع Node وFirebase CLI وJava 21:

```powershell
npm --prefix test/emulator ci
firebase emulators:start --only firestore,auth --project demo-goodfood-chef --config firebase.chef-emulator.json
```

وفي PowerShell ثانية:

```powershell
$env:FIRESTORE_EMULATOR_HOST='127.0.0.1:8787'
$env:FIREBASE_AUTH_EMULATOR_HOST='127.0.0.1:9099'
node test/emulator/seed_chef_workflow.mjs --profiles-only
```

الخيار profiles-only يجهز حسابَي Auth للشيف وسجلي users ووجبة، ولا ينشئ طلبات.
البيانات التجريبية داخل المحاكي فقط؛ الطلب يُنشأ لاحقًا من العميل بصلاحياته.
حسابا الاختبار المحليان: chef-a@local.test وchef-b@local.test، وكلمة مرورهما
ChefLocal123! لا تستخدم هذه الحسابات خارج المحاكي.

## تجربة Chrome والواجهات الحالية

```powershell
flutter run -d web-server --web-hostname 127.0.0.1 --web-port 8188 --dart-define=USE_FIREBASE_EMULATORS=true
```

افتح **http://localhost:8188**، وليس عنوان IP. إصدار FlutterFire Web الحالي
يعيد توصيل Auth بالمحاكي مبكرًا عند استعادة الجلسة على localhost؛ يحظر فحص
التهيئة استخدام عنوان آخر في وضع المحاكي بدل فقدان جلسة الضيف بصمت.

1. افتح العنوان في ثلاث جلسات متصفح مستقلة: Chrome للعميل وEdge للشيف A
   وChrome الخفي للشيف B مثلًا. تبويبان في الملف نفسه ليسا هويتين مستقلتين،
   وكل نوافذ Chrome الخفية المفتوحة معًا تشترك في جلسة واحدة.
2. في جلسة العميل اختر Customer ثم أدخل بيانات الطاولة، وافتح Menu وأضف الوجبة
   إلى Cart وأكمل Checkout واختر طريقة الدفع. تظل الواجهات الحالية كما هي.
3. افتح Orders من القائمة أو Track Your Order من التأكيد. في جلستي الشيف
   اختر Staff وسجل دخول كل حساب؛ يظهر الطلب في New Orders لكليهما.
4. اقبل الطلب من A: يختفي من B ويظهر ضمن My Active Orders لدى A. حوّله إلى
   Ready من A وراقب تحديث شاشة العميل دون إعادة فتحها.
5. أعد تحميل صفحة العميل على العنوان والمنفذ وملف المتصفح نفسيهما؛ يجب أن
   يعود الطلب من استعلام الملكية دون IDs محلية. عميل في ملف رابع جديد لا يراه.
6. اختبارات الرفض المباشر والتنافس المتزامن وتسجيل الخروج تُشغّل آليًا أدناه؛
   غياب زر في الواجهة وحده ليس إثباتًا للأمان.

## Samsung A56 أو Android فعلي عبر USB

فعّل USB debugging، وصّل الهاتف، ووافق على اتصال الحاسوب. لا تحتاج فتح منافذ
المحاكي على شبكة Wi-Fi؛ نستخدم adb reverse مع loopback.

```powershell
$adb='D:\Development\Android\Sdk\platform-tools\adb.exe'
& $adb devices -l
$deviceId='ضع_معرف_الهاتف_هنا'
& $adb -s $deviceId reverse tcp:8787 tcp:8787
& $adb -s $deviceId reverse tcp:9099 tcp:9099
flutter run -d $deviceId --debug --dart-define=USE_FIREBASE_EMULATORS=true
```

اختر Customer على الهاتف وأنشئ الطلب، واستخدم جلستي Chrome المنفصلتين للشيفين
كما سبق. المضيف الافتراضي 127.0.0.1؛ أُوقف التحويل التلقائي إلى 10.0.2.2 حتى
يعمل الهاتف الفعلي عبر USB. إعداد HTTP محدود بعناوين loopback في موارد Android
debug فقط؛ لا يغير شبكة release. لمحاكي Android بلا adb reverse يمكن تمرير
--dart-define=FIREBASE_EMULATOR_HOST=10.0.2.2.

للتحقق من الاستعادة، أغلق التطبيق وافتحه مجددًا دون حذف بياناته أو إعادة تثبيته.
اترك محاكيات Firebase تعمل خلال التجربة. إعادة تشغيل محاكيات جديدة بلا بيانات
ليست اختبارًا لاستعادة التطبيق؛ قاعدة المحاكي مؤقتة ما لم تُصدّر وتُستورد محليًا.
لا تجمع نسخة الإنتاج والتجربة في جلسة واحدة؛ أوقف التطبيق تمامًا عند تغيير الوضع.

## الاختبارات الآلية وحدودها

```powershell
$env:FIRESTORE_EMULATOR_HOST='127.0.0.1:8787'
node --test test/emulator/customer_chef_security.test.mjs
```

تستخدم هذه الاختبارات سياقات Auth اختبارية مع قواعد Firestore الحقيقية على
المحاكي. تثبت عزل القراءة والملكية، رفض تزوير الإنشاء، ثبات محتوى الطلب،
تحديث الدفع مرة واحدة، صلاحيات الشيف، المستندات القديمة، والتنافس. الحالة
الأخيرة توثق عمدًا أن السعر المقدم من العميل ليس سعر قائمة موثوقًا.

هدف Flutter منفصل يستخدم Auth Emulator وFirestore Emulator وFirebase SDK الفعلي:

```powershell
flutter run -d web-server --web-hostname 127.0.0.1 --web-port 8189 --dart-define=USE_FIREBASE_EMULATORS=true -t test/emulator/customer_chef_web_smoke.dart
```

افتح http://localhost:8189 في ملف متصفح اختباري مستقل. المرحلة الأولى تنشئ
طلبات عبر CustomerOrderCubit الفعلي وتقبلها وتجهزها. عند ظهور needsReload:true
أعد تحميل الصفحة مرة واحدة. المرحلة الثانية تتحقق من UID والطلب بعد إعادة
التحميل، ثم تنفذ signOut وتمسح القائمة وتنشئ هوية عميل أخرى وتثبت رفض قراءة
المعرف السابق. النتيجة النهائية CUSTOMER_CHEF_RESULT تحتوي passed:true.
هذا الهدف ينفذ تسجيل خروج داخل جلسة الاختبار فقط، ولا يُستورد من تطبيق الإنتاج.

اختبارات Flutter ذات FakeFirestore تختبر منطق Cubit والنموذج والتنقل وحالات
الواجهة؛ لا تثبت الأمان وحدها. اختبار SDK السابق والقواعد يختبران الأمان على
المحاكي. لا توجد نتيجة تحقق من الإنتاج أو هاتف فعلي حتى الآن.

## حواجز الإنتاج ومراجعة الفريق

- تُراجع customer_chef.rules.proposed مع قواعد الإنتاج الفعلية بواسطة الفريق؛
  ليست منشورة ولا مرجعًا لـ firebase.json. يلزم اعتماد حقل الملكية والمصادقة
  والانتقال التشغيلي للعملاء القدامى. الطلب القديم غير المملوك لا يكتسب مالكًا
  من الاسم أو الطاولة أو IDs محفوظة، ولا يُعرض للضيف تلقائيًا.
  القواعد الجديدة سترفض إنشاء طلب من نسخة عميل قديمة لا ترسل customerId؛
  يجب تنسيق طرح النسخ والقواعد وعدم اعتبار توافق قراءة النموذج سماحًا بكتابة قديمة.
- تفعيل Anonymous provider في مشروع حي خطوة مستقلة لم تُنفّذ. يجب مراجعة
  سياسة الاحتفاظ بالحسابات المجهولة؛ حذف الحساب أو فقدان الجلسة يفقد الوصول،
  والربط المستقبلي بحساب دائم يحتاج الحفاظ على UID أو ترحيلًا موثوقًا منفصلًا.
- قواعد هذا النموذج المحلي تتحقق من كل صنف ضمن **خمسة أصناف مختلفة** بحد أقصى
  لتبقى تحت حد تعبيرات Firestore. هذا قيد محلي موثق يحتاج مراجعة سياسة السلة
  أو نقل التحقق إلى خدمة موثوقة قبل الإنتاج؛ لا يُطرح كقرار أعمال نهائي.
- الأسعار ووجود الوجبات والإجماليات لا تُحسب من مصدر موثوق بالخادم عند الإنشاء.
  القواعد تتحقق من البنية والحدود واتساق subtotal + service_charge مع total
  وثباتها بعد الإنشاء، لكنها لا تقارن الأسعار بقائمة المطعم أو تحسب مجموع
  الأصناف/الضريبة المعتمد. العميل الخبيث يستطيع تقديم سعر منخفض متسق؛ هناك
  اختبار يثبت هذا الحد صراحة. يلزم منطق backend موثوق قبل استخدام مالي إنتاجي.
- لا توجد بوابة دفع موثقة في هذا الربط. payment_data لا يعني paid، ولا يحق
  للعميل تسجيل تحصيل أو تعديل طريقة الدفع مرة ثانية تحت سياسة هذه الدفعة.
- لم يحدث deploy أو تغيير بيانات إنتاج أو commit أو push أو merge.

## النتائج المنفذة

- نجحت 100 حالة unit/widget في جميع ملفات اختبار Flutter غير الفارغة، بما فيها
  FakeFirestore لهوية العميل، والنموذج، وCubit، واستعادة الشيف وAdmin، وحالات
  الشاشتين بالعربية والإنجليزية. هذه الاختبارات ليست إثبات تفويض بالخادم.
- فشلت محاولة flutter test الشاملة بسبب ملف سابق فارغ بلا main:
  test/features/customer_order_management/checkout_order_confirmed_responsive_test.dart.
  لم يُعدّل هذا الملف. أُعيد تشغيل جميع الملفات غير الفارغة ونجحت المئة حالة.
- نجحت تسعة اختبارات قواعد التكامل الجديدة على المحاكي، وثمانية اختبارات
  مقترح الشيف الأصلي كتحقق منفصل من عدم تغير بروتوكول الإسناد.
- نجح هدف Flutter Web الفعلي مع 18 تحققًا، منها إنشاء العميل بصلاحياته،
  تنافس شيفين، تحديث العميل لحظيًا، وإعادة تحميل صفحة حقيقية مع بقاء UID
  والطلب، ثم تسجيل الخروج وعزل هوية عميل جديدة حتى مع معرفة ID القديم.
- flutter analyze بلا أخطاء، مع 21 ملاحظة قائمة (5 تحذيرات و16 info).
- لم تُختبر بيئة إنتاج، ولم يوجد جهاز Android متصل عند فحص adb devices.
  لا يُعد اختبار Chrome إثباتًا لتشغيل أو إعادة تشغيل هاتف فعلي.
- نجح بناء Android بالأمر flutter build apk --debug --no-pub
  --dart-define=USE_FIREBASE_EMULATORS=true. الناتج المحلي
  build/app/outputs/flutter-apk/app-debug.apk؛ نجاح البناء ليس اختبار تشغيل للهاتف.
