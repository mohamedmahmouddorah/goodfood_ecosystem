# عقد إسناد الطلبات للشيف — للمراجعة

تحديث: أُضيف تكامل هوية العميل وملكيته محليًا فقط؛ راجع
[دليل العميل والشيف](customer-chef-local-testing.md). فقرة حدود العميل أدناه
تصف مقترح الشيف المنفصل الأصلي، بينما يستخدم إعداد المحاكي الآن قواعد التكامل
customer_chef.rules.proposed. لم تتغير قواعد الإنتاج أو تُنشر.

حالة هذه الدفعة: تم تنفيذ الربط محليًا بناءً على موافقة تقنية من صاحب الطلب،
مع بقاء مراجعة الفريق مطلوبة قبل الدمج. لا تعني هذه الموافقة اعتماد الفريق
أو اعتماد النشر. أصبح /chef يستخدم ChefOrdersRepository وChefOrdersCubit
الفعلِيَّين، وأُضيفت الحقول الاختيارية إلى OrderModel الحالي.
قواعد الإنتاج وبياناته لم تُعدّل. القواعد المقترحة مستقلة وغير منشورة.

## التوافق المطلوب من الفريق

تُضاف إلى مستندات `orders` والنموذج المشترك الحالي أربعة حقول اختيارية:

| الحقل | النوع | المعنى |
| --- | --- | --- |
| acceptedByChefId | string أو null | UID الفعلي من Firebase Authentication |
| acceptedByChefName | string أو null | نسخة الاسم من users/{UID} وقت القبول |
| acceptedAt | Timestamp أو null | توقيت الخادم عند قبول الطلب |
| readyAt | Timestamp أو null | توقيت الخادم عند جعله جاهزًا |

الحقول الغائبة في الطلبات القديمة تعني null، ولا تتغير قيم OrderStatus الحالية.
لا توجد عملية نقل أو تعبئة تلقائية للطلبات القديمة. الحقول الجزئية غير المتسقة
لا تُعامل كطلب جديد قابل للاستحواذ.

القبول يبدأ التحضير مباشرة: pending وغير مسند ← معاملة قبول ← preparing ومسند.
الشيف المالك فقط ينقل preparing إلى ready. لا توجد أزرار لتسليم أو إلغاء الطلب.
لا يتغير الاسم المحفوظ لاحقًا إذا تغير اسم الشيف في سجل الموظفين.

## هوية الشيف

المصدر هو FirebaseAuth.currentUser.uid وسجل users/{UID} الذي يستعمله تسجيل الدخول
حاليًا. يجب أن يكون role = Chef وstatus = Active والاسم غير فارغ.
معرّف uid المضمّن داخل بيانات المستخدم، أو الاسم المحلي، أو اختيار نوع الجهاز،
أو وجود مستند في مجموعة chefs ليس إثباتًا للصلاحية.

إدارة الطهاة الحالية تستخدم chefs ومعرّفات مستقلة؛ إنشاء سجل هناك لا ينشئ حساب
Firebase Authentication ولا يمنحه صلاحية. يلزم الفريق التأكد من ربط حسابات
الموظفين المعتمدة بسجلات users/{UID}. هذا التغيير لا ينشئ حسابات أو مجموعات.

## قواعد Firestore المقترحة

ملف chef_assignment.rules.proposed مستقل، وإعداد الإنتاج firebase.json لا يشير
إليه. لا يُنشر دون موافقة ومراجعة القواعد المنشورة فعليًا.

الاختبار المحلي يستخدم firebase.chef-emulator.json ومشروع demo-goodfood-chef فقط.
المقترح يسمح للشيف النشط بقراءة قائمة pending وبقراءة طلباته المسندة، ويمنع
الاستحواذ على طلب مسند أو إكمال طلب شيف آخر أو تغيير الأسعار/الأصناف/الملكية.
الاسم والتوقيت يتحقق منهما الخادم. العملاء وغير المسجلين لا يستطيعون تعديل الطلبات.

الاستعلام المشترك يعتمد status = pending ليشمل الطلبات القديمة التي لا تحتوي
acceptedByChefId. الواجهة تستبعد أي pending مسند أو ذي حقول إسناد غير متسقة.
قائمة الطلبات الشخصية تعتمد acceptedByChefId = UID، ثم تُصفّى الحالات محليًا؛
لا يتطلب ذلك نشر فهرس مركّب جديد.

إذا سُحب الطلب من صلاحيات القراءة بعد قبول شيف آخر له، قد يرجع Firestore
permission-denied للمتنافس الخاسر بدل snapshot جديد. يعرض العميل رسالة أن
الطلب لم يعد متاحًا ويعيد تحميل الطوابير، ولا يحاول فرض تحديثه.

## حدود تكامل العميل

قواعد المستودع الحالية لا تتضمن orders أو هوية ملكية للعميل الضيف. معرّفات
الطلبات المحفوظة على الجهاز ليست دليل تفويض. المقترح لا يفتح القراءة للضيوف
ولا يخترع حقل ملكية عميل أو يغيّر مسار إنشاء الطلبات.

قبل النشر يجب دمج المقترح مع عقد إنشاء/قراءة العملاء المعتمد وقواعد الإنتاج
الموجودة، والتأكد من أن الموظف لا يستطيع تعديل دوره أو تفعيل نفسه. ربط تحديث
ready بعرض العميل لا يتطلب حالة جديدة: المستند نفسه يحدّث مستمع الطلبات الحالي.
أي اختبار مراقبة ببيئة محاكي ذات صلاحيات إدارية لا يثبت صلاحيات عميل إنتاج.

## تشغيل اختبارات القواعد محليًا

يتطلب Node.js وFirebase CLI وJava 21. من جذر المشروع:

```sh
npm --prefix test/emulator ci
firebase emulators:exec --only firestore --project demo-goodfood-chef --config firebase.chef-emulator.json "node --test test/emulator/chef_assignment.test.mjs"
```

هذه اختبارات لقواعد مقترحة وبروتوكول المعاملة باستخدام Firebase JavaScript SDK.
ليست إثباتًا بأن القواعد منشورة، أو أن عميل Flutter متصل بالإنتاج.

## تجربة لوحة Flutter بحسابَي شيف فعليَّين على المحاكي

1. شغّل المحاكيين واتركهما يعملان في الطرفية الأولى:

```sh
firebase emulators:start --only firestore,auth --project demo-goodfood-chef --config firebase.chef-emulator.json
```

2. في PowerShell ثانية، أنشئ بيانات اختبار محلية فقط:

```powershell
$env:FIRESTORE_EMULATOR_HOST='127.0.0.1:8787'
$env:FIREBASE_AUTH_EMULATOR_HOST='127.0.0.1:9099'
node test/emulator/seed_chef_workflow.mjs
```

هذا الأمر محمي بعنوانَي المحاكي ومشروع demo-goodfood-chef. ينشئ حسابَي Auth
محليين، وسجلات users المرتبطة بمعرّفاتهما الفعلية، ووجبة وطلبين تجريبيين.
الطلبات ينشئها مدير الاختبار؛ لا يُنسب إنشاؤها إلى عميل ضيف مفوّض.
إعادة تشغيل الأمر تعيد الطلبين التجريبيين إلى pending داخل المحاكي فقط.

3. شغّل التطبيق المحلي:

```sh
flutter run -d chrome --dart-define=USE_FIREBASE_EMULATORS=true
```

في هذا الوضع يُستخدم مشروع demo منفصل منطقيًا داخل المحاكي، ولا تُستخدم
إعدادات Firebase للإنتاج. يُفصل صندوق السلة وتُعطّل قائمة SQLite المحلية
لتجنّب مزج بيانات تجربة المحاكي بكاش الإنتاج. التشغيل العادي دون هذا الخيار
يحافظ على إعدادات التطبيق الأصلية؛ أوقف التطبيق تمامًا عند تغيير الوضع.

4. اختر وضع الموظفين وسجّل الدخول بـ chef-a@local.test ثم chef-b@local.test
في جلستي متصفح معزولتين (مثل متصفح عادي وآخر خفي، أو ملفَّي تعريف منفصلين).
كلمة المرور المحلية للحسابين: ChefLocal123! هذه بيانات محاكي فقط.
لا تستخدم تبويبين يشتركان في تخزين Auth نفسه لاختبار هويتين مستقلتين.

5. يجب أن يرى الحسابان الطلبين في «طلبات جديدة». اقبل طلبًا من A؛ يختفي
من قائمة B ويظهر ضمن طلبات A الحالية. زر «جاهز» متاح لـ A فقط، ثم ينتقل
الطلب إلى الجاهزة. أعد تحميل الجلسة للتحقق من بقاء الإسناد.

## اختبار مستودع Dart عبر Firebase SDK الحقيقي

بعد تجهيز البيانات المحلية، يمكن تشغيل هدف اختبار مستقل عن الإنتاج:

```sh
flutter run -d chrome --dart-define=USE_FIREBASE_EMULATORS=true -t test/emulator/chef_repository_web_smoke.dart
```

يشغّل هذا الهدف المستودع الفعلي بحسابَي Auth وتطبيقَي Firebase منفصلين،
ويختبر اشتراك الطوابير والقبول والتجهيز والتنافس وإعادة إنشاء المستودع.
كما يختبر قارئ CustomerOrdersRepository بصلاحية الشيف المالك ليثبت وصول
حالة ready من المستند نفسه. هذا ليس اختبار صلاحية ضيف حقيقي.
يعرض نتيجة JSON في الشاشة والسجل تحت CHEF_EMULATOR_RESULT.
قبل إعادة الاختبار أعد تشغيل أمر تجهيز البيانات لإرجاع الطلبين إلى pending.

## نتائج التحقق المحلي

- نجحت اختبارات Flutter البالغ عددها 92، بما فيها توافق المستندات القديمة، وهوية الشيف،
  المستودع، وحالات واجهة الشيف، والترجمة، واختبارات طلبات العميل القائمة.
- نجحت اختبارات قواعد Firestore الثمانية على المحاكي، بما فيها التنافس ومنع تعديل طلب شيف آخر.
- نجح اختبار Flutter Web باستخدام Firebase SDK الفعلي مع محاكِي Auth وFirestore:
  حسابان مستقلان، فائز واحد عند التنافس، وقت خادم، منع المنافس، وصول ready إلى قارئ الطلبات،
  وبقاء الإسناد بعد إعادة إنشاء المستودع.
- هذه اختبارات آلية محلية؛ لم تُختبر بيانات الإنتاج، أو صلاحيات ضيف حقيقي، أو إعادة تشغيل هاتف فعلي.
  لا تعني النتائج موافقة الفريق أو نشر القواعد المقترحة.

## ما يبقى مطلوبًا لمسار عميل ← شيف كامل

القواعد المقترحة تمنع إنشاء الطلبات وقراءتها من الضيف، كما تمنع العملاء من
قبولها أو تجهيزها. لذلك سيُرفض إتمام الطلب من واجهة العميل على هذا المقترح
حتى يعتمد الفريق عقد هوية/تفويض العميل ويختبره ويُدمج مع قواعده.
لا تُعطّل القواعد ولا تفتح orders للجميع لتجاوز ذلك.

بعد اعتماد ذلك العقد في بيئة اختبار: ينشئ العميل طلبًا من Menu ← Cart ←
Checkout؛ يلتقطه الشيف من الطابور ويقبله ويجعله جاهزًا؛ يراقب العميل حالته
من /orders عبر معرّف الطلب الحقيقي. الكود الحالي يعيد استخدام المستند
والحالات نفسها، ويعرض اسم الشيف المحفوظ عند وصوله. لكن صلاحيات العميل
والإنشاء من واجهته تحتاج اختبارًا متكاملًا منفصلًا بعد اعتماد العقد.
